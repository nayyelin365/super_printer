Architecture proposal

Giving every kitchen its own floor

Right now the app runs as one shared kitchen: one employee roster, one batch counter, one receiving log. This plan splits that into per-location rooms — each location gets its own staff, its own Sushi Rice batches, its own receiving log — while every screen, printer, and alarm keeps working exactly as it does today.

Scope Employees · Sushi Rice SOP · Receiving Log · Log Sheet Shipped in 6 independent phases New infrastructure None — same Firebase project

01Two calls we made up front

Decided

One shared database, tagged by location

Every record gets a kitchenLocationId. No new Firebase project to stand up, no config to switch when a device moves between locations — the app just asks which kitchen it's for once, and filters from there.

Decided

UI-level separation, for now

Locations stay invisible to each other on screen. There's no login system today, so this isn't a hard security wall — see the note below before this ships to anyone outside the business.

02What a batch code looks like after

Sushi Rice and Receiving Log codes get printed on real thermal labels and QR codes that can leave the building. Today's format only knows the date, so two kitchens making rice on the same day would print identical batch numbers. Each location gets a short code baked into every printed ID from here on.

03How a new kitchen gets on the roster

A device isn't handed a location — it registers one, from Settings → Kitchen Location. The first device at a brand-new site fills this in once; every device after that just picks the name from a list. That list, and this form, is also what the sidebar switcher and the first-launch screen both reuse — one form, three doors in from the app.

04How the rollout is staged

Each phase ships and gets used on its own before the next one starts. Nothing downstream depends on a phase that hasn't been confirmed working with real data first.

1
Foundation — register & pick a kitchen
The location list, the Settings registration form, the first-run gate, a switcher in the sidebar. Nothing is filtered yet — every screen still shows everything, so there's zero risk to what's already running.
2
Employees
Existing staff get assigned to the current kitchen automatically; the employee form gains a Location field so new hires are matched on purpose, and the roster splits by location from here on.
3
Sushi Rice SOP
Batches, the dashboard, and the HACCP log sheet all split by kitchen. Scanning a printed label still works from any device — the code alone is enough to find it.
4
Receiving Log
Invoices and their items split by kitchen, including the combined "every item, every invoice" view the list screen uses.
5
Log Sheet
The general log entries split by kitchen the same way — the smallest of the four, saved for last on purpose.
6
Rules follow-up
Register the new location list with Firestore's access rules, and bring the security question below back to the table as its own conversation.

05What changes on screen

  • Home screen — pick a kitchen on first launch
  • Sidebar — switch kitchens anytime
  • Employee form — choose a Location when adding staff
  • Employee roster & QR badges
  • Sushi Rice dashboard, batches, HACCP report
  • Receiving Log & its item list
  • Log Sheet entries

Stays exactly as is

  • Alarms — lives on the device, not the cloud
  • Printer connection & settings — same, per device
  • Label designs and print flow
  • Everything already working today

06One thing to know before this goes live

▲
Attention: this separates kitchens on screen, not on the server.

There's no staff login today, so nothing stops a device from technically reaching another kitchen's data directly — the app just never shows it to you. Fine if every location is the same trusted business. If two locations should never be able to see each other's data even on purpose, that needs a login system added first — a separate project, quoted on its own.
